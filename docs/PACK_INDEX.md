# 📡 DWCode pack index — the install contract

**Schema 1.** One file, one job: tell a DWCode client exactly what it may download, from where,
and how to prove the bytes are the bytes that were described.

```
https://dwcode.pages.dev/data/catalog/index.json          the index
https://dwcode.pages.dev/data/catalog/index.json.sha256   checksum of the exact bytes above
```

Generated by `node tools/catalog.mjs index` from the licence gate plus the first-party pack
artifacts. Validated by `node tools/catalog.mjs check` (CI) and, independently, by
`PackIndex::parse()` in `src/packindex.cpp` — the app never trusts a file merely because CI did.

## 1. Shape

```jsonc
{
  "kind": "dwcode-pack-index",          // constant; anything else is refused
  "schema": 1,                          // constant; a newer schema is refused, not guessed at
  "generated": "2026-10-25",            // UTC date the file was written
  "app": { "min": "0.1.0" },            // oldest DWCode that may consume this index
  "base": "https://dwcode.pages.dev",   // where this file was served from
  "gate": { "checked": 206, "eligible": 179, "pending": 0, "refused": 20, "absent": 7 },
  "entries": [
    {
      "id": "cybercore.dwcode-core",    // unique, publisher.name, lowercase-safe
      "name": "DWCode Core Signal",
      "publisher": "cybercoretech",
      "version": "0.1.0",               // X.Y.Z
      "family": "themes",
      "kind": "pack",                   // "pack" | "reference"
      "tier": "declarative",
      "license": "MIT",                 // short SPDX form
      "licenseFull": "MIT",             // exactly what the upstream licence file says
      "verified": true,                 // licence file was read, not just a registry field
      "capabilities": [],               // permission strings a consent screen must show
      "upstream": "https://github.com/cybercoretech/dwcode",
      "registry": null,                 // Open VSX listing, or null for first-party
      "download": {
        "url": "https://github.com/cybercoretech/dwcode/releases/download/v0.1.0/dwcode-core-0.1.0.dwpack",
        "sha256": "72f03131b96d1b8d9ca0da17b7ad4ecca4c250a82db570b5845e6439cece81e0",
        "size": 4096
      }
    }
  ]
}
```

`kind` tells the client what the row *is*:

| `kind` | meaning | `download` |
| --- | --- | --- |
| `pack` | a DWCode-native artifact DWCode will fetch, verify, unpack and load | **required**, non-null |
| `reference` | a licence-checked third-party package. Facts only — DWCode does not redistribute it, and an install is an act at the publisher's registry | **required to be `null`** |

`tier` is the compatibility report from the blueprint: `declarative` · `reference` ·
`needs language server` · `requires DWCode host`.

## 2. Fail-closed rules

Both the generator's `check` and `PackIndex::parse()` enforce every one of these; a violation
refuses the whole file rather than dropping the offending row.

1. `kind === "dwcode-pack-index"` and `schema === 1`, exactly. No forward-compatibility guessing:
   a future format must ship a new `schema` and a client that understands it.
2. Every entry has `id`, `name`, `publisher`, `version`, `family`, `kind`,
   `tier`, `license`, `licenseFull`, `capabilities` (array of strings).
   `version` is semver — `^\d+\.\d+\.\d+(-prerelease)?(+build)?$`. Pre-releases
   are real (`1.0.0-rc.1` is published on Open VSX today) and a client that
   refused them would be unable to describe half the registry.
3. `id` is unique across the file. `kind` is one of the two values above.
4. `kind === "pack"` ⟺ `download` is an object; `kind === "reference"` ⟺ `download` is `null`.
5. `download.url` is an absolute URL. Scheme must be `https` — except `http` when the host is
   loopback (`127.0.0.1`, `::1`, `localhost`), which is what a test server serves. Any other
   scheme (`file:`, `ftp:`, `data:`) is refused.
6. `download.sha256` is 64 lowercase hex characters. `download.size` is an integer
   `1 ≤ size ≤ 67108864` (64 MiB — a declarative pack is kilobytes; anything larger is a bug or
   an attack).
7. A `reference` row may carry `upstream: null` (two publishers publish no repository), but must
   then carry a `registry` URL — something has to be credited.
8. Unknown extra keys inside `download` are refused; extra keys at entry level are ignored but
   logged by `check` so typos surface.

## 3. Provenance and integrity

* `index.json.sha256` holds `<64 hex>  index.json\n` — the checksum of the exact bytes. A client
  that fetched the index over TLS records this value as `indexSha256` in the lock record, so an
  install can always be traced back to the index version that authorized it.
* Authenticity (a signature over the index, with a key pinned in the binary) is **Phase 5**.
  Until then integrity is: TLS in transit + per-artifact `sha256` + a recorded `indexSha256`.
  This is stated plainly rather than implied.

## 4. The artifact: `.dwpack`

An **uncompressed POSIX ustar archive** of one pack directory. No gzip, no zip — nothing that
needs a library the app does not already link, and nothing that hides its contents.

Writer: `node tools/build-pack.mjs` (own tar writer in `tools/tar.mjs`, so the layout is exact
and byte-reproducible). Reader: `PackStore::extractTar()` in `src/packstore.cpp`.

Rules — the writer obeys all of them and the reader enforces all of them:

* Format `ustar\0` (magic `ustar`, version `00`). 512-byte blocks, no PAX/GNU extensions.
* Only two entry types: `'0'` regular file and `'5'` directory. **Everything else is refused** —
  no symlinks, hardlinks, devices, or FIFOs, ever.
* Names are relative, POSIX-separated, ≤ 100 bytes, no leading `/`, no `..` segment, no empty
  segment. Directories are stored explicitly (type `'5'`), files after their directory.
* `mode` `0000644` (files) / `0000755` (dirs), `uid`/`gid` `000000`, `uname`/`gname` empty,
  `mtime` `0`, device numbers `000000`.
* Size is an octal ASCII field; a file of size 0 is legal. The archive ends with **two** 512-byte
  zero blocks, and the writer never emits a third of non-zero data.
* Header checksum is computed the classic way: checksum field filled with 8 spaces, sum all 512
  bytes, stored as 6-digit octal + NUL + space. The reader recomputes and refuses a mismatch.
* The whole archive is then hashed: the resulting `sha256` is what `download.sha256` pins.

## 5. Lock record

`installed.json`, in `PackLoader::userDirectory()` beside the packs it describes. Versioned and
fail-closed in the same style as the session journal: a corrupt or unknown-schema file refuses
*writes* and reports the error — it is never silently reset to empty.

```jsonc
{
  "schema": 1,
  "packs": {
    "cybercore.dwcode-core": {
      "version": "0.1.0",
      "sha256": "…",            // of the artifact actually unpacked
      "indexSha256": "…",       // of the index that authorized it
      "origin": "https://…",    // download url
      "installedAt": "2026-10-25T12:00:00Z",
      "enabled": true,
      "capabilities": []
    }
  }
}
```

## 6. Lifecycle rules the client must honour

1. **No URL-based installs by default.** An install only ever starts from an `entries[]` row that
   passed `parse()`. A pasted URL, a `file://` path, or a bare filename is a *local import*, which
   runs the identical manifest + licence + integrity + compatibility checks and is a separate,
   explicit action.
2. Download to a temporary file. Hash it. **Only on a match** move it into place. A mismatch
   deletes the file and reports; it never lands on disk as an installed pack.
3. Unpack into a temporary directory, validate the whole tree with the existing `PackLoader`
   rules, and only then move it into the pack directory. Partial unpacks are never visible.
4. Consent before first enable: licence + capability list, exactly as the index declares them.
   A pack whose manifest asks for a capability the index did not declare is refused.
5. Updates are opt-in and show the capability diff before re-consent.
6. Every state change rewrites the lock record atomically (write temp, then rename).

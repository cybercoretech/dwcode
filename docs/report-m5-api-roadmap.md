## 1. What the Install (M5) buttons need

The button is not one feature. It is five, and today **zero** of them exist in the app:

1. **An index to point at.** A machine-readable catalog: per entry `id, version, origin URL,
   sha256, SPDX licence, upstream repo, compatibility tier, capability list`. The human-readable
   version already ships at `https://dwcode.pages.dev/repository` (172 cards) and is generated by
   `node tools/catalog.mjs build` from the licence gate. The machine-readable twin is one
   `catalog/index.json` emission away.
2. **A place the bytes live.** Catalog *metadata* wants a CDN/static host; the *pack files* want
   GitHub Releases (immutable, checksummed, tied to a tag).
3. **A client that fetches + verifies.** `QNetworkAccessManager` GET → compare `sha256` against the
   index → write a lock record (origin, version, hash) in the same versioned, fail-closed style as
   the existing session journal → unpack into the pack directory → hand to the existing
   `packloader` validation. Step 3's last clause is free: `packloader` already rejects malformed
   manifests, path escapes, and over-capability declarations.
4. **Consent.** Download → show the capability/permission list and the licence → *then* enable.
   Updates are opt-in and must show the capability diff before re-consent (a pack that gains a new
   permission is a security event, not a routine bump).
5. **Lifecycle.** install · enable/disable (the Settings → EXTENSIONS toggle from M1 already
   exists) · update · uninstall, all reflected in the same lock record.

### The channel decision — and what your Open VSX account changes

Three channels, different jobs:

| Channel | Right for | Wrong for |
| --- | --- | --- |
| **`dwcode.pages.dev` static JSON** | catalog **metadata**: search, counts, licence, links. Already built, already CDN'd, ETag-friendly for free. | hosting binary-ish artifacts |
| **GitHub Releases** (blueprint's choice) | **DWCode-native packs**: exact version, tag, `sha256`, immutable. | discovery/search |
| **Open VSX** | a real, published **registry**: your own packs get a URL, a version, a licence field and an `ovsx` publish flow — plus it is where the 172 catalog rows *already live* as source data. | running VS Code executable extensions in DWCode (we are not a VS Code fork — no ext host) |

**Recommended combination:** pages.dev serves the **index**, GitHub Releases serves the **packs**,
Open VSX serves as **ingest + your publishing venue**. Ingest matters: CI can pull a VSIX from Open
VSX, extract only the declarative parts (themes, grammars, snippets, tmLanguage for `tm2monarch`),
strip publisher artwork, record the SPDX id, and emit a DWCode-native pack with provenance. That is
how the 172-row catalog becomes installable without ever executing third-party code.

**And now, with an account:** publish *your own* declarative pack first
(`ovsx publish -p <file>.vsix` with `OVSX_PAT`), under a namespace such as `cybercoretech`. That is
the fastest way to have a real end-to-end Install path: our pack → Open VSX → fetched by DWCode →
verified → loaded by `packloader`. Namespace must be claimed before the first publish.

**Hard blockers before any button can go live:** no `v0.1.0` tag · no `index.json` · no HTTP fetch
in `packloader` · no lock record · no consent dialog for downloads.

## 2. The API question

### 2.1 Should DWCode have one?

Yes — but **not a server you host.** DWCode is local-first; a cloud API in front of a code editor
means cost, operations, and shipping users' file data through your infrastructure. What DWCode needs
is *one contract served over three transports*:

1. **In-process (already have it):** the Qt WebChannel bridge — editor UI ⇄ C++. Zero sockets, zero
   serialization cost, type-checked on both sides. This stays the primary API for the desktop UI.
2. **Loopback HTTP `/v1` (new):** bind `127.0.0.1` only, per-session token, JSON over POST. This is
   what the **Android app**, scripts, CI tools and your own hand-made extensions talk to when they
   are on the same machine/network as the editor.
3. **Static JSON (new, no server logic):** the catalog/install content API. Scales to any number of
   extensions at ~zero cost because a CDN serves it. This is the part that must survive "growing
   very quickly."

> **Most efficient possible, in one line:** *JSON-RPC 2.0 as the message envelope, on top of a
> loopback-only HTTP endpoint, plus a static checksummed JSON index for everything read-only.*

Why JSON-RPC and not plain REST: DWCode **already has a JSON-RPC implementation** — that is what
LSP uses, and the LSP client ships today. One request format, one id/params/result shape, one place
to add batching and server-push notifications (progress, diagnostics, install events). A single
`POST /v1/rpc` endpoint also means the Android client multiplexes everything over one connection
instead of churning round trips.

Concrete surface:

```
GET  /v1/health                      → version, capabilities
GET  /v1/catalog?since=<etag>        → static index (or a 304)
POST /v1/rpc                         → JSON-RPC 2.0 envelope:
     pack.install {id, version, sha256}
     pack.list / pack.enable / pack.disable / pack.remove
     workspace.open / document.read / document.write
     lsp.request / terminal.run
```

Rules that keep it fast and safe as you grow:

* **Versioned from day one** (`/v1`), changes strictly *additive*; a breaking change is `/v2`. Never
  mutate a field's meaning under the Android app's feet.
* **Loopback-only + token.** Generate a random token at startup, require it on every call, send no
  `Access-Control-Allow-Origin: *`. Deny by default.
* **Static reads are cached** (`ETag`/`If-None-Match`) — the catalog must never be a dynamic query.
* **Schema is the contract:** `docs/openapi.yaml` (HTTP surface) + `docs/json-rpc.md` (envelope),
  both committed, both validated in CI. The client and the server are written against the file, not
  against each other's current behaviour.

### 2.2 Your three ideas, honestly

| Idea | Verdict | Why |
| --- | --- | --- |
| **[actix.rs](https://actix.rs/)** | ❌ **Not for DWCode** | actix is a *Rust web framework*. DWCode is C++17 + Qt6. Adopting it means a second language, a second toolchain, a second process boundary, and a Rust↔C++ seam — all to do what `QTcpServer` + 300 lines already does. It only earns its place if you ever ship a **separate** Rust backend service, and even then the Rust ecosystem's current mainstream choice is **axum** (same authors, tokio-native; actix's actor framework has slowed). Do not take it on for this. |
| **[Bruno](https://www.usebruno.com/)** | ✅ **Use it** | A FOSS API client that stores requests as plain files in your repo — no cloud account, no proprietary collection format, diffs cleanly in Git. Perfect fit: commit `api/dwcode/*.bru` next to `openapi.yaml`, open it when testing `/v1`, and it doubles as living documentation for whoever joins later. |
| **[Swagger Editor](https://swagger.io/open-source/swagger-editor/)** | ✅ **Use it, in file mode** | Free (Apache-2.0), runs in the browser, and gives you validation + a readable rendered doc as you type. Use it to *author and validate* `docs/openapi.yaml`, commit the YAML, and lint it in CI. Skip the hosted Swagger UI/registry — you do not need another service, and your API is loopback-only anyway. |

**Net recommendation:** Swagger Editor to author `docs/openapi.yaml`, CI to validate it, Bruno to
exercise it, no framework — the HTTP layer stays inside Qt.

## 3. Honest opinion: agentforge · ferraxis · diagprint

All three are Rust, all pushed today, all effectively single-maintainer at 0 stars. Treat them as
*sibling experiments*, not dependencies.

### `agentforge` — the one worth building on ⭐
*"Local-first, model-agnostic agentic software-development environment."*
**Best of the three by a distance.** MIT, `0.3.1-alpha` with a real tagged release, attested builds
+ SBOM, CI, `PROJECT_SPEC`/`PROJECT_STATE`, docs, contribution guide. Crucially, its core idea —
plans, task contracts, **explicit permissions**, isolated worktrees, quality-gate evidence, audit
records, human decisions as the source of truth instead of the model — is *precisely* the shape
DWCode's executable extension host needs (blueprint M2/M4: capability permissions, consent,
audit).
**Risk:** it is alpha; APIs will churn; a hard crate dependency from a C++ app is a non-starter.
**How to use it:** adopt the *model* (permission/audit schema, the "capability requested → human
consents → recorded" flow), not the code. If you want the code, it must talk to DWCode over the same
loopback JSON-RPC contract as everything else. **Confidence it works for us: high**, if kept at
arm's length.

### `ferraxis` — the one to not plan around 🛑
*"An independent Rust compiler implementation."*
**No `LICENSE` file at all.** That is not a small oversight: without an OSI licence, nobody —
including you on another machine — may use, redistribute or modify it. It defaults to all rights
reserved. Fix that before anyone else touches it, or it cannot be a Cybercore deliverable.
Setting the licence aside: a compiler front/middle/back end at "Phase 0" is a multi-year research
project (rustc is a team and roughly a million lines). It will not produce anything DWCode can use
inside any roadmap timeframe you have described. **Confidence it works for us: very low.**
Only realistic connection: if it ever emits diagnostics, it becomes a great stress corpus for
`diagprint`.

### `diagprint` — quietly useful, if you adopt the schema 🛠️
*"A Rust diagnostics lifecycle framework — structured diagnostics, rendering, remediation, CI,
editors, telemetry."* Apache-2.0, on crates.io, documented on docs.rs. The idea is right: DWCode
already renders LSP diagnostics in a problems panel, and an extension API, the output panel and CI
all want the *same* diagnostics shape (`severity, code, message, range, source, fixes`).
**Risk:** it is Rust and the DWCode host is C++, so it only pays off if you either (a) standardise
on its JSON schema and emit/consume that from C++, or (b) run a small Rust helper process. A Rust
crate you cannot link is a Rust crate you do not have.
**Confidence it works for us: medium** — high value *if* you commit to one shared diagnostics JSON
shape; near-zero if it stays a Rust-only library nobody calls.

**One rule for all three:** DWCode hard-depends only on components that have (1) an OSI licence
file, (2) a tagged release, (3) CI. Today: agentforge ✓✓✓ · diagprint ✓✓✓ · ferraxis ✗✗✗.

## 4. The phase plan

### Phase 0 — Foundations *(this week, unblocks everything)*
- [ ] Tag `v0.1.0` on `dwcode.pro`'s `VERSION` and `git push origin v0.1.0`.
- [ ] `gh release create v0.1.0` with the source tarball + `dwcode-0.1.0-x86_64.tar.gz`
      (from `packaging/aur/make-bin-tarball.sh`).
- [ ] Register the SSH key with the AUR account, run `tools/aur-release.sh` (no more
      `--allow-missing-tag`), commit the regenerated `packaging/aur/*`.
- [ ] Claim an Open VSX **namespace**, publish the first DWCode declarative pack with `ovsx`.
- [ ] Emit `site/data/catalog/index.json` from `tools/catalog.mjs` (id, version, origin, sha256,
      SPDX, upstream, tier, capabilities) and deploy it with the site.
- **Exit:** every install precondition that is *not* code exists. Gates: `validate:catalog`,
  `catalog:scan`, `grammar:test`, `validate:packs`.

### Phase 1 — Install, read-only (M5 core)
- [ ] `src/packloader.cpp`: `fetch(indexUrl)` with `ETag`, sha256 verify, lock record, unpack,
      re-validate with the existing pack validator. **No URL-based installs**; only index entries.
- [ ] Consent dialog: licence + capability list before the first enable.
- [ ] Enable/disable already exists (M1) — wire it to the lock record; add uninstall.
- [ ] UI: `install · M5` becomes `install`, `installed`, `update available`.
- [ ] Tests: adversarial cases as `backend_test` functions — hash mismatch, truncated download,
      manifest with a path escape, index entry whose licence is pending, pack that claims a
      capability the index did not declare (must fail closed).
- **Exit:** a first-party pack installs end-to-end from the published index, verified, on a clean
  machine. Suites stay green (backend 10/10, UI 14/14).

### Phase 2 — The contract (`/v1`)
- [ ] Author `docs/openapi.yaml` in Swagger Editor; `docs/json-rpc.md` for the envelope.
- [ ] Implement loopback `/v1` in Qt (`QTcpServer` + the existing JSON-RPC plumbing), token auth,
      `127.0.0.1` only, deny-by-default routing.
- [ ] Commit a Bruno collection under `api/` covering health, catalog, pack.install, document.*
      and make CI run a smoke pass against a headless instance.
- [ ] Contract tests: an unknown method returns a JSON-RPC error, never a crash; `/v1` never
      answers without the token.
- **Exit:** an external tool can drive DWCode without touching the UI. Breaking-change policy
  documented.

### Phase 3 — Android client
- [ ] Android reads the **static content API** first: catalog, search, pack details, install
      instructions. Zero backend, ships fast, exercises the CDN path you will need anyway.
- [ ] Optional companion mode: same-phone/LAN client speaking `/v1` with the token (QR/pairing
  handshake), reusing the exact JSON-RPC schema from Phase 2.
- [ ] Version negotiation: client sends `X-DWCode-API: 1`; server keeps `/v1` additive forever.
- **Exit:** the app browses and installs against production without any Android-specific
  back-end code.

### Phase 4 — Executable extension host (M2/M4) + agentforge model
- [ ] `src/extensionbroker.{h,cpp}` per the blueprint, with the permission/consent/audit flow
      borrowed from **agentforge's** model (schema-level, not a crate dependency).
- [ ] Threat model in `tests/threatmodel.md`; adversarial tests forced on in CI.
- [ ] Custom hand-made extensions: publish them as first-party packs through the *same* Phase 0
      pipeline — no privileged back door for our own code.
- [ ] Consider `diagprint`'s diagnostics JSON shape as the shared contract for problems panel +
      extension reporting — only if adopted in C++ too.
- **Exit:** one executable extension runs under an explicit, recorded consent. Licence gate passes.

### Phase 5 — Scale & hardening
- [ ] Signed index (minisign/cosign over `index.json`), pinned keys in the app; a licence change
      becomes a re-review, not a silent bump.
- [ ] Publish the catalog ecosystem-by-ecosystem as rows clear review (the gate already automates
      the licence check: `206 checked · 179 eligible · 0 pending`).
- [ ] Rate/size limits, incremental index (`?since=`), telemetry-free download counters.
- [ ] Public API docs generated from `openapi.yaml` into the site.
- **Exit:** 10× the catalog with no change to install latency and no new failure mode.
